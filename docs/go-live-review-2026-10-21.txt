VERIFIED PENDING FINDINGS

P1 — Failed refunds cannot recover automatically.
Files/functions: server/services/payments.js refundCancelledOrder (lines 86–110);
server/controllers/orderController.js handleRazorpayWebhook;
server/services/paymentMaintenance.js runPaymentMaintenance.
Cause: refund submission response status is ignored; any valid identity/amount is stored
PENDING. Later checks fetch the payment but never inspect the stored refund ID's status.
PENDING is excluded from claims, and refund.failed events have no explicit handler.
Impact: a terminal failed refund can remain awaiting confirmation indefinitely.
Verified with isolated database and controlled provider response status=failed: two
calls leave PENDING/refundRequired=true, with only one provider submission.
Fix: fetch stored refund status; explicitly handle pending/processed/failed and signed
failure events. Surface confirmed failure and alert an operator. Permit a new logical
refund attempt only after terminal failure and cumulative refunded amount are verified;
keep same-key retries for uncertain outcomes. Add pending-to-failed, replay and race tests.

P1 — Already-refunded payments cannot reconcile when capture was missed.
Files/functions: server/services/payments.js reconcilePayment (lines 41–52), applyRefund;
server/controllers/orderController.js handleRazorpayWebhook;
server/services/paymentMaintenance.js runPaymentMaintenance.
Cause: reconciliation finds captured payments only and throws for a paid provider order
whose payment is already refunded. The refund webhook lookup requires the local payment
ID that the missed capture never persisted.
Impact: provider can be fully refunded while local state stays pending/cancelled; repeated
reconciliation cannot repair it without manual intervention.
Verified with isolated pending order and provider paid order/full-refunded payment:
reconcilePayment rejects and local payment remains PENDING.
Fix: validate identity/order/amount/currency and provider refund evidence; atomically record
payment identity and final refund status, cancel/release any remaining reservation, and
write one audit entry. Add reversed callback ordering and missed-capture recovery tests.

P1 — Backend secrets remain tracked in Git.
Files: server/.env; .gitignore. client/.env is also tracked, although frontend config is
not inherently secret. Verified backend fields include JWT_SECRET, MONGO_URI and
RAZORPAY_KEY_SECRET; values were not printed. Actual disclosure outside repository access
is NOT established.
Fix: remove backend env from tracking while retaining local configuration, use a secret
store and sanitized example, rotate potentially exposed credentials, and assess repository
history/access. Do not assume .gitignore alone removes existing files/history.
